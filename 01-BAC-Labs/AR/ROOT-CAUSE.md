# أسباب ثغرات التحكم بالوصول (Root Cause Analysis)

## 1. نظرة عامة
ثغرات **Broken Access Control** لا تحدث بسبب خطأ في التشفير أو أخطاء في الـ Syntax، بل هي **أخطاء معمارية ومنطقية (Architectural & Business Logic Flaws)** في تصميم التطبيق وطريقة معالجته لهوية المستخدم وصلاحياته عبر دورة حياة الطلب.

---

## 2. الأسباب الجذرية التقنية الخمسة

### 1. الخلط بين التحقق من الهوية (Authentication) وفحص الصلاحية (Authorization)
هذا هو السبب الأكثر شيوعاً. يضع المطور طبقة حماية تتأكد من أن المستخدم "سجل دخوله بنجاح"، لكنه يفترض ضمنياً أنه طالما سجل دخوله، فهو مسموح له بإجراء أي عملية!
```php
// كود مصاب: يتحقق فقط من وجود جلسة مسجلة!
session_start();
if (!isset($_SESSION['user_id'])) {
    die("يرجى تسجيل الدخول أولاً");
}
// كارثة: أي شخص مسجل دخوله يستطيع حذف أي مستخدم!
$userIdToDelete = $_POST['target_user'];
deleteUserFromDatabase($userIdToDelete);
```

### 2. تخزين حالة الصلاحيات لدى العميل (Client-Side State Storage)
الاعتماد على الكوكيز، أو التخزين المحلي (LocalStorage)، أو حقول الـ HTML المخفية لتحديد هل المستخدم أدمن أم لا. بما أن المتصفح بالكامل تحت سيطرة المستخدم، فإن أي قيمة مخزنة لديه هي قيمة قابلة للتزوير التام.

### 3. ثغرة الإسناد الجماعي (Mass Assignment / Over-Posting)
تحدث في أطر العمل الحديثة (Laravel, Spring Boot, ASP.NET, Express) عندما يقوم المطور بربط كائن الطلب (Request Object) مباشرة بجدول قاعدة البيانات دون تحديد قائمة بيضاء بالحقول القابلة للتعديل. يستطيع المهاجم تمرير `"role": "admin"` أو `"roleid": 2` في جسم الـ JSON فيقوم الـ ORM بحفظها مباشرة.

### 4. التناقض بين خادم التوجيه الخارجي (Proxy) وخادم التطبيق (Origin)
تستخدم الشركات خوادم Reverse Proxy أو WAF لفحص الروابط وحظر `/admin`. لكن إذا كان خادم التطبيق الداخلي يدعم ترويسات قديمة مثل `X-Original-URL` أو `X-Rewrite-URL`، فإن البروكسي يرى الطلب موجهاً إلى `/` ويسمح به، بينما الباك إند يعيد كتابة الرابط إلى `/admin` وينفذ العملية بدون علم البروكسي!

### 5. التحقق المنفصل على مستوى المسار وليس وحدة التحكم (Route vs Controller Check)
تطبيق الفحص على مسار الـ `POST` فقط دون الـ `GET`، أو فحص الصلاحية في بداية شاشات المعالج (Wizard Step 1) ونسيان فحصها في الخطوات الفرعية التالية، معتمدين على افتراض زائف بأن المستخدم لا يمكنه الوصول لـ Step 2 إلا بالمرور بـ Step 1.
