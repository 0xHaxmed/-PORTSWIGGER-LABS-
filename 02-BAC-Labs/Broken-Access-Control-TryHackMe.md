## 📗 Task 2 – مقدمة عن Broken Access Control

### أولاً: إيه هو Access Control؟

هو الآلية اللي بتحدد **مين مسموحله يوصل لإيه**. أربع أنواع رئيسية:

| النوع | الفكرة بشكل مبسط |
|---|---|
| **DAC** (Discretionary) | صاحب المورد نفسه هو اللي يحدد مين يدخل (زي الملك اللي يوزّع مفاتيح القلعة) |
| **MAC** (Mandatory) | قواعد صارمة ثابتة محددة من جهة عليا، مفيش استثناءات (زي الحصن العسكري) |
| **RBAC** (Role-Based) | الصلاحية مبنية على "الدور الوظيفي" للشخص (مدير، موظف مبيعات...) |
| **ABAC** (Attribute-Based) | الصلاحية مبنية على **صفات متعددة**: الوقت، الموقع، الجهاز... إلخ |

### ثانياً: أنواع ثغرات Broken Access Control

1. **Horizontal Privilege Escalation** – مستخدم عادي يوصل لبيانات مستخدم عادي تاني (نفس المستوى)، غالباً بالتلاعب في ID في الرابط.
2. **Vertical Privilege Escalation** – مستخدم عادي يوصل لصلاحيات أعلى منه (أدمن)، غالباً بالتلاعب في حقل مخفي أو parameter.
3. **Insufficient Access Control Checks** – السيرفر مش بيتأكد من الصلاحية بشكل كامل أو ثابت في كل الطلبات.
4. **IDOR (Insecure Direct Object References)** – استخدام معرّفات (IDs) يسهل تخمينها للوصول لموارد مش مفروض توصلها.

### 🧭 منهجية حل أسئلة Task 2 (مش الإجابات)

- كل سؤال في الأساس هو **تعريف مصطلح** ذُكر حرفياً في نص الـ Task، اقرأ الفقرات تاني وركّز على الجملة اللي فيها كلمة "occurs when" أو التعريف المباشر.
- للأسئلة اللي بتسأل عن الاختصار الكامل (زي IDOR, ABAC, RBAC)، دور على أول مرة اتكتب فيها الكلمة كاملة في النص (عادة بتكون جنب الاختصار بين قوسين).
- الفرق بين Horizontal و Vertical: اسأل نفسك "هل الهجوم وصل لمستوى صلاحية **أعلى**؟" لو آه → Vertical، لو نفس المستوى بس لمستخدم تاني → Horizontal.

## 📕 Task 4 – تقييم التطبيق (Reconnaissance)

### الفكرة
التطبيق فيه 3 أجزاء رئيسية: **Register** → **Login** → **Dashboard**.

خطوات أي pentester في الغالب:
1. يعمل تسجيل حساب جديد (Register).
2. يسجل دخول ويراقب الطلبات اللي بتتبعت للسيرفر.
3. يستخدم **Burp Suite / OWASP ZAP** في وضعية الـ **Proxy** لالتقاط الـ HTTP Requests/Responses.

### الملاحظات المهمة من تحليل الـ Traffic:
- عند تسجيل الدخول، بيتبعت طلب لملف `functions.php`.
- الرد بييجي بصيغة **JSON** وبيحتوي على: `status`, `message`, `first_name`, `last_name`, `is_admin`, و `redirect_link`.
- التطبيق بيستخدم `redirect_link` عشان يوجّه المستخدم لصفحة `dashboard.php` ومعاها **parameter** اسمه مرتبط بالصلاحيات.
- مفيش أي **Security Headers** محطوطة، يعني مفيش خط دفاع أول.
- السيرفر: Apache 2.4.38 على Debian / Linux، والباك إند PHP 8.0.19.

### 🧭 منهجية حل أسئلة Task 4

| السؤال | إزاي توصله |
|---|---|
| نوع السيرفر | افتح تبويب **Response Headers** في Burp Suite بعد أي طلب، هتلاقي header اسمه `Server` فيه اسم الويب سيرفر |
| اسم الـ parameter اللي فيه رابط التحويل في رد الـ JSON | ارجع لرد `functions.php` اللي جه بعد Login، دوّر على الحقل اللي قيمته شبه رابط (URL) |
| موديول Burp Suite اللي بيلقط الطلبات | ده اسم التبويب الأساسي اللي بتستخدمه لاعتراض الترافيك (مش Repeater ولا Intruder) |
| إيميل الأدمن | لازم تدور في صفحة أو جدول فيه قائمة بالمستخدمين "Online Users" داخل الـ Dashboard نفسه، مش في الـ Burp |

## 📓 Task 5 – استغلال التطبيق (Exploitation)

### فكرة الاستغلال خطوة بخطوة:

1. **اعترض الـ Response** بتاع طلب الـ Login باستخدام Burp Proxy (Intercept).
2. لاحظ قيمة `redirect_link` — هتلاقيها غالباً بتحتوي على parameter بقيمة `false` (يعني مش أدمن).
3. **جرّب تغيّر القيمة من `false` إلى `true`** يدوياً، وابعت الطلب المُعدَّل (Forward).
4. لاحظ: هل اتنقلت لصفحة جديدة مختلفة عن الـ Dashboard العادي؟ (دي أول إشارة لثغرة Vertical Privilege Escalation).
5. لو وصلت لصفحة إدارية (admin.php)، دوّر على أي عنصر تحكم بيسمحلك تغيّر صلاحيات حسابك بنفسك (checkbox / toggle) واحفظ التغييرات.
6. بعد ما تاخد صلاحية أدمن، دوّر جوه الصفحة الإدارية على أي نص أو شكل غريب يبدأ بـ `THM{...}` — ده شكل الـ flags في TryHackMe عادة.

### 🧭 منهجية حل أسئلة Task 5

| السؤال | إزاي توصله |
|---|---|
| نوع تصعيد الصلاحيات اللي حصل | فكّر: مستخدم عادي وصل لصفحة أدمن = وصول لمستوى **أعلى** من مستواه → ارجع لتعريفات Task 2 |
| اسم الـ parameter اللي فتحلك صفحة الأدمن | هو نفس الحقل اللي لاحظته في رد الـ JSON في Task 4 (اللي غيّرت قيمته من false لـ true) |
| الـ Flag | لازم توصله بنفسك عملياً بعد تنفيذ خطوات الاستغلال كاملة جوه بيئة الـ Lab — مفيش طريقة توصله غير بالتنفيذ الفعلي |

> ⚠️ ملحوظة: الـ Flags الفعلية بتتغير أحياناً حسب نسخة المكنة، فأفضل طريقة هي تنفيذ الخطوات بنفسك في بيئتك.

## 📒 Task 6 – إجراءات الحماية (Mitigation)

أهم الحلول اللي المطورين لازم يطبقوها:

### 1️⃣ تطبيق RBAC بشكل صحيح
تحديد الأدوار (admin, editor, user) والصلاحيات المرتبطة بكل دور، والتأكد من فحصها **في كل طلب** مش مرة واحدة بس.

```php
$roles = [
    'admin'  => ['create', 'read', 'update', 'delete'],
    'editor' => ['create', 'read', 'update'],
    'user'   => ['read'],
];

function hasPermission($userRole, $requiredPermission) {
    global $roles;
    return in_array($requiredPermission, $roles[$userRole]);
}
```

### 2️⃣ استخدام Prepared Statements
لمنع SQL Injection اللي ممكن تؤدي لتجاوز التحقق من الهوية:

```php
$stmt = $pdo->prepare("SELECT * FROM users WHERE username=? AND password=?");
$stmt->execute([$username, $password]);
```

### 3️⃣ إدارة الجلسات (Session Management) بشكل آمن
- استخدام كوكيز آمنة
- تحديد مدة صلاحية للجلسة (Session Timeout)
- التحقق من آخر نشاط للمستخدم

### 4️⃣ ممارسات برمجة آمنة
- التحقق من صحة أي مدخل (Validation & Sanitization)
- تخزين كلمات المرور بـ `password_hash()` مش دوال قديمة زي `md5()`

> 🔑 **المبدأ الأهم**: التحقق من الصلاحية لازم يكون **Server-Side** في كل طلب، مش الاعتماد على إخفاء الروابط أو التحقق من جهة الـ Client فقط (زي القيمة اللي كانت بترجع في JSON وسهل تتغير).

## 📔 Task 7 – الخلاصة

### أهم النقاط اللي اتعلمناها:
- **Broken Access Control** = فشل النظام في تطبيق قيود الوصول الصحيحة.
- **Horizontal Escalation** → خطر لأنه بيسمح بالتحرك الجانبي (Lateral Movement) بين حسابات بنفس المستوى.
- **Vertical Escalation** → أخطر، لأنه ممكن يوصل لسيطرة كاملة على النظام.
- التأثير العام: فقدان بيانات، تعطيل خدمات، اختراق كامل للشبكة.

## 🗺️ خلاصة المنهجية العامة لحل أي سؤال في الغرفة

1. **اقرأ النص قبل السؤال مباشرة** – معظم الأسئلة النظرية إجابتها موجودة حرفياً في الفقرة اللي قبلها.
2. **للأسئلة العملية (زي الـ Flag)** – لازم تنفذ الخطوات فعلياً في بيئة الـ Lab، مفيش شورت كت.
3. **استخدم Burp Suite Proxy** لمراقبة كل Request/Response، وركّز بالذات على:
   - الـ Headers (للسيرفر ونوعه)
   - الـ Body (لأي بيانات JSON فيها معلومات حساسة)
4. **جرّب تغيّر القيم** (زي true/false في البراميترز) وراقب رد فعل السيرفر — ده أساس اكتشاف أي Broken Access Control.
5. لو وصلت لصفحة أو وظيفة مش مفروض توصلها، وثّق الخطوات (Screenshot + Request) عشان تقدر تشرحها في تقرير احترافي لو كانت دي مهمة Pentest حقيقية.
